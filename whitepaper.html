1. Introduction

Le Règlement Général sur la Protection des Données (RGPD) impose aux responsables de traitement de mettre en œuvre des mesures techniques appropriées pour protéger les données personnelles (Article 32). Le chiffrement est explicitement cité comme une mesure de pseudonymisation (Article 4, paragraphe 5) et comme une mesure de sécurité appropriée.

Cependant, chiffrer des colonnes en base de données pose un problème fondamental : les données chiffrées ne sont plus interrogeables. Une colonne email chiffrée en AES-256-GCM ne peut plus être utilisée dans un WHERE email = 'dupont@example.com', ni dans un WHERE email LIKE '%dupont%'.

Ce document présente une solution complète utilisant lib_sina_crypt, la bibliothèque de chiffrement au niveau du champ de SINAINSIGHT, avec deux techniques qui restaurent la capacité de recherche sur données chiffrées :

  • Les indices aveugles (blind index) pour la recherche exacte
  • Les indices trigrammes (N-gram index) pour la recherche partielle

2. Le problème : chiffrement vs recherche

2.1 Chiffrement classique

Le chiffrement AES-256-GCM est un chiffrement authentifié : il garantit la confidentialité et l’intégrité des données. Chaque opération de chiffrement produit un ciphertext différent grâce au nonce (nombre utilisé une seule fois).

Chiffrement("dupont@example.com") → "aG9tZSBpbiB0..."  (run 1)
Chiffrement("dupont@example.com") → "bXVzdCBoYXZl..."  (run 2)

Conséquence : même valeur en clair → ciphertexts différents. Impossible de faire un WHERE ou un index.

2.2 Le dilemme des entreprises

Approche Confidentialité Recherche Conformité RGPD
Pas de chiffrement Non Oui Non (Art. 32)
Chiffrement intégral Oui Non Oui mais inutilisable
Chiffrement + blind index Oui Exacte Oui
Chiffrement + trigrammes Oui Partielle Oui

3.2 Exemple de chiffrement RGPD (C)

#include "sina_crypt.h"

// Chiffrement d'un champ RGPD pour stockage en base
const char *email = "dupont@example.com";
size_t msg_len = strlen(email);
uint8_t buffer[4096];
size_t output_len;
memcpy(buffer, email, msg_len);
sina_rgpd_crypt(buffer, sizeof(buffer), msg_len, &output_len);

// Déchiffrement
size_t dec_len;
sina_rgpd_decrypt(buffer, sizeof(buffer), output_len, &dec_len);
buffer[dec_len] = '\0';
// buffer == "dupont@example.com"

3.5 API RGPD

Pour le chiffrement des données personnelles en base de données, lib_sina_crypt fournit une API dédiée RGPD disponible dans les trois langages :

Langage Chiffrement RGPD Déchiffrement RGPD
C sina_rgpd_crypt() sina_rgpd_decrypt()
Go sinacrypt.RGPDCrypt() sinacrypt.RGPDDecrypt()
Python sina_crypt.rgpd_crypt() sina_crypt.rgpd_decrypt()

Ces fonctions chiffrent en AES-256-GCM avec un nonce strictement monotone. Chaque appel de chiffrement d’une même valeur en clair produit un ciphertext différent (nonce unique), mais tous se déchiffrent correctement.

Le chiffrement est authentifié : un message altéré ou déchiffré avec le mauvais CLIENT_NUMBER provoque une erreur (vérification du tag GCM), jamais un déchiffrement partiel ou corrompu.

Tous les exemples de ce document utilisent cette API RGPD.

4. Indices aveugles (Blind Index)

4.1 Principe

Un indice aveugle est un hash HMAC-SHA256 du texte en clair, calculé avec une clé secrète dédiée aux indices. Il produit une empreinte déterministe : même entrée → même hash, ce qui permet l’égalité (=) et le JOIN, mais ne révèle pas le contenu.

HMAC-SHA256("dupont@example.com", clé_index)
  → "a3f8c9d1e2b4..."  (toujours le même)

Propriétés de sécurité :

  • Le HMAC ne peut pas être inversé (fonction à sens unique)
  • Sans la clé d’index, l’attaquant ne peut pas pré-calculer les hashes
  • L’indice révèle uniquement l’égalité : deux lignes avec le même hash ont la même valeur en clair, mais la valeur reste inconnue

4.2 Schéma de base de données

PostgreSQL

CREATE TABLE clients (
    id              SERIAL PRIMARY KEY,
    -- Données chiffrées (AES-256-GCM via lib_sina_crypt)
    email_encrypted TEXT NOT NULL,
    nom_encrypted   TEXT NOT NULL,
    iban_encrypted  TEXT NOT NULL,

    -- Indices aveugles (HMAC-SHA256)
    email_blind_idx CHAR(64) NOT NULL,
    nom_blind_idx   CHAR(64) NOT NULL
);

CREATE INDEX idx_clients_email ON clients(email_blind_idx);
CREATE INDEX idx_clients_nom   ON clients(nom_blind_idx);

MongoDB

db.createCollection("clients")
db.clients.createIndex({ "email_blind_idx": 1 }, { unique: true })
db.clients.createIndex({ "nom_blind_idx": 1 })

4.3 Insertion d’un enregistrement

import (
    "crypto/hmac"
    "crypto/sha256"
    "encoding/hex"
    sinacrypt "gitlab.com/sina_project_group/lib_sina_crypt/go"
)

// Clé secrète dédiée aux indices aveugles (différente de la clé AES)
var blindIndexKey = []byte("votre-cle-index-secrete-32-octets")

func blindIndex(plaintext []byte) string {
    mac := hmac.New(sha256.New, blindIndexKey)
    mac.Write(plaintext)
    return hex.EncodeToString(mac.Sum(nil))
}

func InsertClient(email, nom, iban string) error {
    // Chiffrement des données
    emailEnc, _ := sinacrypt.RGPDCrypt([]byte(email))
    nomEnc, _   := sinacrypt.RGPDCrypt([]byte(nom))
    ibanEnc, _  := sinacrypt.RGPDCrypt([]byte(iban))

    // Calcul des indices aveugles
    emailIdx := blindIndex([]byte(email))
    nomIdx   := blindIndex([]byte(nom))

    // Insertion en base
    _, err := db.Exec(`
        INSERT INTO clients
            (email_encrypted, nom_encrypted, iban_encrypted,
             email_blind_idx, nom_blind_idx)
        VALUES ($1, $2, $3, $4, $5)`,
        emailEnc, nomEnc, ibanEnc, emailIdx, nomIdx)
    return err
}

4.4 Recherche par indice aveugle

func FindClientByEmail(email string) (*Client, error) {
    idx := blindIndex([]byte(email))

    row := db.QueryRow(`
        SELECT email_encrypted, nom_encrypted, iban_encrypted
        FROM clients
        WHERE email_blind_idx = $1`, idx)

    var emailEnc, nomEnc, ibanEnc []byte
    if err := row.Scan(&emailEnc, &nomEnc, &ibanEnc); err != nil {
        return nil, err
    }

    // Déchiffrement
    emailDec, _ := sinacrypt.RGPDDecrypt(emailEnc)
    nomDec, _   := sinacrypt.RGPDDecrypt(nomEnc)
    ibanDec, _  := sinacrypt.RGPDDecrypt(ibanEnc)

    return &Client{
        Email: string(emailDec),
        Nom:   string(nomDec),
        IBAN:  string(ibanDec),
    }, nil
}

Performances : la recherche utilise l’index B-tree standard de la base de données. Le temps de recherche est identique à une recherche sur colonne non chiffrée, plus le temps de déchiffrement (0,02 ms par champ).

5. Indices trigrammes (N-gram Index)

5.1 Principe

Les indices aveugles ne supportent que l’égalité exacte. Pour une recherche partielle (LIKE '%dupont%'), on utilise des indices trigrammes : le texte en clair est découpé en sous-chaînes de 3 caractères (trigrammes), et chaque trigramme est hashé individuellement.

"dupont" → {"dup", "upo", "pon", "ont"}
         → {HMAC("dup"), HMAC("upo"), HMAC("pon"), HMAC("ont")}

Pour rechercher "pont", on calcule les trigrammes de la requête ({"pon", "ont"}) et on cherche les lignes qui contiennent tous ces trigrammes.

5.2 Schéma de base de données

PostgreSQL avec table de trigrammes

-- Table principale
CREATE TABLE clients (
    id              SERIAL PRIMARY KEY,
    nom_encrypted   TEXT NOT NULL,
    email_encrypted TEXT NOT NULL
);

-- Table des trigrammes
CREATE TABLE client_trigrams (
    client_id   INTEGER REFERENCES clients(id) ON DELETE CASCADE,
    field_name  VARCHAR(32) NOT NULL,
    trigram_idx CHAR(64) NOT NULL
);

CREATE INDEX idx_trigrams ON client_trigrams(field_name, trigram_idx);

MongoDB avec tableau embarqué

// Document client
{
    _id: ObjectId("..."),
    nom_encrypted: "aG9tZSBp...",
    email_encrypted: "bXVzdCBo...",
    nom_trigrams: [
        "a3f8c9d1...",  // HMAC("dup")
        "b2e7d0c3...",  // HMAC("upo")
        "c1d6e4f5...",  // HMAC("pon")
        "d0c5f3e2..."   // HMAC("ont")
    ]
}

db.clients.createIndex({ "nom_trigrams": 1 })

5.3 Génération des trigrammes

func trigrams(s string) []string {
    s = strings.ToLower(s)
    if len(s) < 3 {
        return []string{s}
    }
    result := make([]string, 0, len(s)-2)
    for i := 0; i <= len(s)-3; i++ {
        result = append(result, s[i:i+3])
    }
    return result
}

func trigramIndices(plaintext string) []string {
    tris := trigrams(plaintext)
    indices := make([]string, len(tris))
    for i, tri := range tris {
        mac := hmac.New(sha256.New, blindIndexKey)
        mac.Write([]byte(tri))
        indices[i] = hex.EncodeToString(mac.Sum(nil))
    }
    return indices
}

5.4 Insertion avec trigrammes

func InsertClientWithTrigrams(nom, email string) error {
    nomEnc, _   := sinacrypt.RGPDCrypt([]byte(nom))
    emailEnc, _ := sinacrypt.RGPDCrypt([]byte(email))

    // Trigrammes du nom
    nomTrigrams := trigramIndices(nom)

    // PostgreSQL : insertion + trigrammes
    tx, _ := db.Begin()
    var id int
    tx.QueryRow(`INSERT INTO clients (nom_encrypted, email_encrypted)
                 VALUES ($1, $2) RETURNING id`,
                 nomEnc, emailEnc).Scan(&id)

    for _, tri := range nomTrigrams {
        tx.Exec(`INSERT INTO client_trigrams
                 (client_id, field_name, trigram_idx)
                 VALUES ($1, 'nom', $2)`, id, tri)
    }
    return tx.Commit()
}

5.5 Recherche partielle par trigrammes

func SearchClientsByName(query string) ([]Client, error) {
    queryTrigrams := trigramIndices(query)
    if len(queryTrigrams) == 0 {
        return nil, fmt.Errorf("requete trop courte")
    }

    // Construire la requête : tous les trigrammes doivent matcher
    // (intersection des ensembles)
    sqlQuery := `
        SELECT c.nom_encrypted, c.email_encrypted
        FROM clients c
        WHERE c.id IN (
            SELECT client_id
            FROM client_trigrams
            WHERE field_name = 'nom'
              AND trigram_idx = ANY($1)
            GROUP BY client_id
            HAVING COUNT(DISTINCT trigram_idx) = $2
        )`

    rows, err := db.Query(sqlQuery, pq.Array(queryTrigrams),
                          len(queryTrigrams))
    if err != nil { return nil, err }
    defer rows.Close()

    var results []Client
    for rows.Next() {
        var nomEnc, emailEnc []byte
        rows.Scan(&nomEnc, &emailEnc)
        nomDec, _   := sinacrypt.RGPDDecrypt(nomEnc)
        emailDec, _ := sinacrypt.RGPDDecrypt(emailEnc)
        results = append(results, Client{
            Nom:   string(nomDec),
            Email: string(emailDec),
        })
    }
    return results, nil
}

Exemple :

Recherche "pont" sur le champ nom :
  "pont" → trigrammes : {"pon", "ont"}
  → HMAC("pon") = "c1d6e4f5..."
  → HMAC("ont") = "d0c5f3e2..."
  → SELECT WHERE trigram_idx IN (...) HAVING COUNT = 2
  → Trouve : "Dupont", "Dupont-Martin", "Pontoise"

5.6 MongoDB : recherche avec $all

// Recherche "pont" dans les noms
var queryTrigrams = trigramIndices("pont")
db.clients.find({
    nom_trigrams: { $all: queryTrigrams }
})

Flux d’écriture :

  1. L’application reçoit les données en clair
  2. sina_rgpd_crypt() chiffre chaque champ sensible
  3. blindIndex() calcule le hash HMAC de chaque champ indexé
  4. trigramIndices() calcule les trigrammes hashés des champs nécessitant la recherche partielle
  5. Les données chiffrées et les indices sont insérés en base

Flux de lecture :

  1. L’application calcule l’indice de la requête (blind ou trigrammes)
  2. La base de données retourne les lignes correspondantes
  3. sina_rgpd_decrypt() déchiffre les champs nécessaires

8. Considérations de sécurité

8.1 Gestion des clés

  • Clé AES : intégrée à la bibliothèque statique, protégée. En production (licence commerciale), chaque client a un CLIENT_NUMBER unique qui dérive une clé AES différente.
  • Clé d’index : clé HMAC-SHA256 séparée, à stocker dans un gestionnaire de secrets (Vault, AWS KMS, etc.).
  • Les deux clés sont indépendantes : compromettre la clé d’index ne compromet pas le chiffrement.

8.2 Limites des indices aveugles

  • Recherche exacte uniquement : impossible de faire LIKE, >, < ou BETWEEN sur un blind index.
  • Fuite d’égalité : un attaquant avec accès à la base voit quelles lignes ont la même valeur (même hash). C’est inhérent à tout schéma de recherche déterministe.
  • Pas de tri : les indices ne préservent pas l’ordre.

8.3 Limites des trigrammes

  • Faux positifs : la recherche par trigrammes peut retourner des résultats non pertinents (mêmes trigrammes, contexte différent). Un filtrage post-déchiffrement est recommandé.
  • Stockage supplémentaire : chaque champ indexé par trigrammes génère len(texte) - 2 hashes de 64 caractères.
  • Requête minimale 3 caractères : les recherches de moins de 3 caractères ne sont pas supportées.

9. Conformité réglementaire

9.1 RGPD

  • Article 32 : le chiffrement est une mesure technique appropriée. lib_sina_crypt utilise AES-256-GCM, recommandé par l’ANSSI.
  • Article 4(5) : les indices aveugles constituent une forme de pseudonymisation — les données ne sont plus directement identifiantes sans la clé de déchiffrement.
  • Article 34 : en cas de violation de données, les données chiffrées ne sont pas considérées comme compromises si la clé n’est pas affectée.

9.2 PCI DSS

  • Exigence 3.4 : les numéros de carte (PAN) doivent être rendus illisibles. Le chiffrement au niveau du champ avec lib_sina_crypt satisfait cette exigence.
  • Exigence 3.5 : les clés de chiffrement doivent être protégées. La clé AES est protégée dans la bibliothèque statique et dérivée du CLIENT_NUMBER.
